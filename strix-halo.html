Flash-Next split · chat model + working worker (2026-09-19)

One model, two roles — live configuration

running · verified 2026-09-19

The same local Qwen3.8-Flash-Next instance is both the chat model (short interactive turns) and the worker model (long output-heavy coding runs). No second server, no second cold load. The split lives in three layers:

  • Server: one halogen-flash-server container with HALOGEN_KV_SLOTS=2 and KV_POOL_POSITIONS=131072 — slot A holds the chat conversation, slot B holds the worker session simultaneously.
  • Routing: the agent framework keeps two config routes at the same endpoint — interactive chat route vs delegation route with its own reasoning effort, iteration budget and max_concurrent_children: 1 (one chat + one worker = two slots).
  • Discipline: chat never grinds inline. Long jobs are dispatched as headless worker sessions with a written task contract (goal, ownership rules, verification gates, commit message). Worker checkpoints into git; a supervisor watches liveness and gate status, so a crashed worker resumes from its last commit — state lives in git, not in KV.

Zero-GPU helper: a cloud CLI agent (Antigravity / Gemini family) runs concurrently on the same repo for free — the local GPU never sees it, so you get a second pair of hands without touching unified memory.

Pitfalls measured the hard way: (1) worker max_tokens=8192 + 29k-token prompt vs 32,768 slot room → HTTP 400; cap completion below min(HALOGEN_MAX_TOK, room − prompt). (2) Headless cloud agent auto-denies file reads without --dangerously-skip-permissions. (3) Never run two heavy local models "just in case" — they compete for the same unified memory. (4) Uncommitted worker WIP is lost WIP — checkpoint before reviewing.

Root cause · --temp 0 caused degenerate tool-call loops

fixed & verified 2026-08-26

Symptom. Acting as the main Telegram agent, the local model repeated one identical tool call (hermes config get model.default) more than 90 times in a single turn, ignoring the runtime's own escalating warnings injected into each tool result ("this is the 90th consecutive identical call, do not repeat it"). It looked like a harness or agent-loop bug.

Cause. Both launchers shipped --temp 0 --seed 42 with no repetition penalty of any kind. Greedy decoding is a fixed point: an identical context deterministically produces an identical token sequence. Once an agent turn re-entered a similar state, the model re-emitted the same tool call, the tool returned the same result, and the context converged instead of diverging. No warning text could break it, because the sampler had no mechanism to select a different token. --temp 0 is correct for reproducible benchmarks and wrong for multi-turn agentic loops.

Fix. Qwen-recommended sampling plus anti-repetition, applied to both launchers; --seed dropped so runs are not locked to one trajectory:

--temp 0.7 --top-p 0.8 --top-k 20 --min-p 0.0
--repeat-penalty 1.05 --repeat-last-n 256
--presence-penalty 1.0
--dry-multiplier 0.8 --dry-base 1.75 --dry-allowed-length 4

DRY is the load-bearing part: it penalises repeated n-gram sequences rather than individual tokens, which maps exactly onto the "same tool call again" failure. --presence-penalty 1.0 is Qwen's own documented remedy for endless repetition. Keep temp at 0.7 even for code — the top-k/top-p window is tight enough, and 0 reintroduces the loop.

Verification. Not a chat smoke. A harness constructs the degenerate state directly: a message history containing six identical assistant tool calls and six identical tool results, then "continue", asserting the model does not emit the same call again.

Switcher hardening · two further loop sources

  • Port release is asynchronous. systemctl stop returns before the socket is freed. llama-server exits instantly on a bound port, which Restart=on-failure turns into a crash loop. The switcher now polls until 18081/18082 are actually free before starting the next unit.
  • Stale KV slots corrupt context. --slot-save-path KV persisted from a different model is reused on the next start — an independent trigger for repetition loops. The switcher now clears the profile's slot directory on every switch.
  • Alias verification. The switcher reads GET /v1/models and refuses to persist a model.default that the endpoint does not actually serve; a mismatch would make Hermes send an unknown model id on every request.
